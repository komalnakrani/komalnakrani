## MLE-CH-15-S01 — Decision and Bench Setup

### Bench Setup

The decision is deliberately narrower than “is this model ready?”: can this exact release candidate be verified from its source and build provenance through authorized promotion to a named previous-good recovery identity? BL-12 supplies an evidence-bound release candidate and BL-13 supplies consumer compatibility. Neither is permission to guess missing package, signer, access, or recovery facts. The incoming state is TECHNICALLY-QUALIFIED; the required dossier delta is `TECHNICALLY-QUALIFIED → RELEASABLE` through BL-14. A technical PASS is evidence for a later release decision, not a self-issued release authorization.

Treat the candidate as a bundle of identities, not a file with a reassuring label. The artifact digest names bytes; source provenance names the materials and build relation; a dependency inventory names the components that became those bytes; a signer or builder expectation names what was checked; authorization evidence names who may invoke promotion; and a previous-good identity names the state to which exposure can return. If any link is absent, the honest result is an unresolved chain. A registry pointer, mutable tag, successful download, or model score cannot substitute for that chain.

The authority route stays explicit. Security owns control requirements and exceptions. Platform owners own shared promotion mechanisms. Package, build, and consumer owners correct their own missing identities. The MLE assembles and tests workload evidence but does not choose trust roots, tailor a control catalog, approve an exception, or make a fleet decision. A mismatch therefore produces HOLD, REJECT, or REOPEN with its discriminating field and owner; it does not produce an improvised repair in this chapter.

The Bench Sheet records the decision, fixed inputs BL-12 and BL-13, the exact candidate identity, the required evidence, the outgoing state, retained owner, and next evidence. Its **state and dossier delta** says that BL-14 may be issued only for the same candidate and declared consumers. Its **next evidence** is a measured serving envelope, which can consume this candidate but cannot weaken its integrity or recovery chain.

The chapter-specific trace is explicit rather than implied: architecture assignments `MLE-CLM-012`, `MLE-CLM-014`, `MLE-CLM-017`, `MLE-CLM-018`, and `MLE-CLM-020`; boundaries `BND-09`, `BND-10`, `BND-11`, and `BND-14`; scenario `SCN-10`; domain `PD-09`. The architecture set binds release identity, evidence continuity, lifecycle change, external authority, and visible limitations. The boundary set keeps security exceptions, shared promotion, package identity, and consumer decisions with their owners; the scenario applies those rules to an integrity/access review; the domain names the resulting integrity, lineage, and recovery capability. This is mapping, not a second claim lesson.

## MLE-CH-15-S02 — Procedure: Build One Inspectable Chain

**Primary teaching MLE-BCLM-043.** A candidate is not releasable until a reviewer can traverse one evidence chain from its exact bytes to an immutable recovery target. That chain ties the subject digest to source revision and build history, enumerates component origins and hashes, records the expected signer or build authority, proves promotion permission, and resolves the prior state that could replace the candidate. Begin with the BL-12 subject and make every packet row point back to it: build record, external parameters, dependency identity, authorization, the BL-13 consumer set, and the previous-good subject. This is not a long checklist for its own sake. Every row must answer whether it describes this candidate or only something with a similar name.

This chain has two useful properties. It makes replacement visible: a changed artifact digest requires a new candidate, not a handwritten correction to an old record. It also makes recovery concrete: “roll back” is an instruction only after the prior package and its evidence packet can be located immutably. MLE-BSRC-030 and MLE-BSRC-031 supply secure-development and control vocabulary; MLE-BSRC-036 supplies provenance verification context. They support a bounded integrity practice, not an organizational trust policy or a release signature from this author.

**Primary teaching MLE-BCLM-044.** Refuse verification whenever a required comparison fails. The provenance subject must resolve to the candidate digest; the signature must satisfy the stated rule; the observed builder and build recipe must match their expectations; and declared external inputs must equal those actually used. Merely storing a provenance document is weaker than checking it. A useful comparison table records expected value, observed value, result, evidence locator, failure reason, owner, and recovery route. An unsigned statement can remain as an observation labelled with weaker assurance, but cannot satisfy a signature requirement. SLSA 1.2 guidance in MLE-BSRC-035 supplies the subject/provenance/expectation sequence, while MLE-BSRC-036 keeps the resulting assurance bounded.

Fail-closed does not mean fail-silent. A subject-digest mismatch tells the package owner to restore an immutable subject or allocate a new candidate. An unexpected builder routes to build and security owners. A missing authorization routes to security or platform authority. In each case, the technical record says what was observed and what remains unsupported. It does not infer model quality, safety, or permission to release from a green provenance check.

**Primary teaching MLE-BCLM-045.** A dependency name is not a dependency identity. Record source, resolver or index precedence, version, digest, and trusted origin, because the same name from an unintended index can enter a candidate without altering a casual package listing. The public PyTorch nightly dependency-confusion mechanism supports this bounded inference through MLE-BSRC-042: an identity rule is needed when source selection can differ beneath a familiar name. It does not establish that all resolvers behave alike or that the disclosed event measures prevalence. A clean inventory that omits origin is a useful index, not proof.

## MLE-CH-15-S03 — Evidence Interpretation and Source Notes

The strongest supportable conclusion is modest: the named candidate has a checked chain for the enumerated artifacts, dependencies, consumers, authorization expectation, and previous-good target. The counterexample is equally instructive. A team can have a valid metric and a registry tag that resolves while a dependency came from an unintended index and the rollback target is a mutable alias. The first facts do not cancel the latter gaps.

Source notes: MLE-BSRC-030 (NIST SSDF 1.1) and MLE-BSRC-031 (NIST SP 800-53 Rev. 5 release 5.2.0) are versioned guidance, not local approval procedures. MLE-BSRC-035 is SLSA Build 1.2 guidance; MLE-BSRC-036 is provenance-verification material; MLE-BSRC-042 is the bounded public package case. The public case supplies mechanism, not an assurance statistic. No source delegates security-exception approval to an MLE.

Currentness matters because commands and products are not the doctrine. The stable fields are identity, origin, expectation, comparison, owner, limitation, and recovery route. Signing systems, SBOM formats, registry APIs, package-manager precedence, and SLSA field guidance require recheck at each freeze. The currentness note belongs in BL-14 so a reader does not mistake a dated verifier command for a permanent control.

**Accepted currentness ledger — verified 2026-08-18.** `MLE-BSRC-030` is SSDF 1.1; recheck for a successor or material errata, and retain that framework scope grants no risk acceptance. `MLE-BSRC-031` is SP 800-53 Rev. 5 release 5.2.0; recheck any new 5.x release, mapping, baseline, or control-text change, and retain that a catalog row proves no workload control. `MLE-BSRC-035` is living SLSA Build verification guidance; recheck subject, signature, builder, expectation, or dependency guidance, while retaining that it defines neither trust roots nor authorization. `MLE-BSRC-036` is SLSA 1.2; recheck a superseding approved version and retain 1.2 when exact fields support the claim, while remembering it says nothing about model quality. `MLE-BSRC-042` is the living PyTorch advisory; recheck corrections, scope, indicators, or an independent final report, and never infer complete consumer cleanup.

The limitations are visible: this packet proves bounded supply-chain and recovery properties for listed objects. It does not prove training validity, consumer behavior, model quality, policy compliance, or a real production outcome. When a requirement asks for any of those, the next action is to route to the appropriate evidence and authority rather than enlarging the conclusion.

There is a practical review order. First resolve the subject and fail if it is mutable or absent. Second compare each provenance field against a locally supplied expectation, keeping both values in the record. Third enumerate every dependency as a tuple rather than a display name. Fourth link the actual authorization evidence and its owner rather than treating access success as approval. Finally, retrieve the previous-good subject and packet by immutable identity. This order prevents a polished narrative from hiding an unresolved root. It also gives a later reviewer a way to reproduce a negative result without relying on memory.

The packet should distinguish a failed comparison from an untested comparison. “Signature missing” and “signature present but not checked” have different evidence states, although neither meets an expected verified signature. “No recovery package named” and “previous-good package named by a mutable alias” are likewise different failures. Precision here is not pedantry: it decides who can repair the condition and whether the next step is a new candidate, a security investigation, a platform action, or an earlier lifecycle gate.

## MLE-CH-15-S04 — Worked Trace: Identity Under Pressure

CASE-01, the Benchline Inspection Dossier, is a FICTIONAL SYNTHETIC CAPSTONE. Its data, results, incidents, and outcomes are constructed; it carries no industrial, safety, performance, or business claim. In its trace, the candidate’s digest, build record, permitted consumer, and previous-good package are fixed fixture fields. The first review finds the same package name in two indexes. The chain remains HOLD until source, version, digest, and index precedence name one intended dependency. This is synthetic-deterministic reasoning, not a production release report.

CASE-04, a constructed deep acoustic event classifier, adds checkpoint and preprocessor identity. The trace makes a wrong checkpoint digest distinguishable from a general “model issue.” CASE-05, a constructed shared-ranking tenant, adds a tenant-compatible consumer and shows why a workload packet cannot claim shared-platform authorization. Both are constructed satellites. Their **reported facts** are none; their **attributed outcomes** are none; their **allowed inference** is limited to the fixture’s identity rule; their **forbidden inference** is any real field performance, SLO, or platform assurance.

CASE-11 is a PUBLIC REPORTED CASE about the disclosed PyTorch package/dependency remediation mechanism. Its reported fact supports an origin-and-precedence tamper lesson. It does not report every consumer’s cleanup, authorize a general threat model, or prove an industry-wide defect rate. Preserve that limitation beside the trace rather than rewriting the incident as a fictional success story.

Keep its truth record separated: **reported facts** are PyTorch’s affected nightly Linux/pip window, malicious same-name package, indicator, and stated mitigations; **attributed outcomes** are PyTorch’s precedence explanation and response, without a complete cleaned-population result; **allowed inference** is that origin, version, digest, provenance, and residual paths belong in release identity; **forbidden inference** is prevalence, universal resolver behavior, complete cleanup, model performance, or prevention by an unevidenced control; **limitations** are first-party reporting, stable packages out of scope, and no verified population-wide outcome; **transfer rule** replaces pip/index mechanics with the port’s actual package path while retaining identity checks, bounded containment, consumer verification, and external authority.

The trace is intentionally a review rehearsal. A reader may point to the digest row and ask what changes if an artifact is rebuilt; the answer is a new identity and a new evaluation of the changed candidate. A reader may point to an authorization row and ask whether a successful role lookup grants an exception; the answer is no, because an external authority record is still required. A reader may point to the previous-good row and ask whether an alias can serve as recovery; the answer is no until it resolves to an immutable, evidence-bearing package. These questions make the packet auditable without making it a security program.

## MLE-CH-15-S05 — Failure Labs

`MLE-CH-15-LAB-01` is synthetic-deterministic and offline. Begin with `signed-package-pass`: the subject digest, expected builder, dependency origin, authorization evidence, and immutable previous-good identity agree. The lab produces a BL-14-shaped PASS record with observed fields and limitation. Replace the expected subject digest with an absent value. The result must be HOLD or REJECT; the lab must not invent a digest from a tag. The diagnostic is “unresolved artifact identity,” and the repair boundary is the package owner.

`MLE-CH-15-LAB-02` injects `unexpected-builder`, `dependency-origin-substitution`, `missing-authorization`, and `mutable-previous-good` fixtures. Each fails for a distinct field. A same-name package from a different index is not repaired by accepting its name. Missing authorization is not repaired by the MLE signing for itself. A mutable rollback label is not treated as a recovery identity. The deterministic record preserves the failed mutation, names security, platform, package, or build owner, and routes re-entry to the applicable gate. Neither lab contacts a provider, changes credentials, trains a model, or asserts a real release.

The closed positive input is `FIX-MLE-CH-15-1`; the closed mutation input is `FIX-MLE-CH-15-2`. Both accept only BL-12, BL-13, the enumerated fixture fields, and fixed expectations. Their legal dispositions are PASS, HOLD, REJECT, or REOPEN. Their acceptance check requires an exact subject, verified expectation, intended dependency origin, external authorization evidence, immutable previous-good identity, limitation, owner, and next route. Prohibited effects are network, shell, provider, credential, model, production, and authority mutation.

Read a synthetic-deterministic lab result as a test of record semantics, not as a claim that an organization has verified its own supply chain. The fixture has a fixed input identity and a deliberately bounded comparison. Its PASS means the fixture contained the specified evidence; its RED path means the injected discrepancy was not silently promoted. The lab is useful because the same observed field, disposition, limitation, and authority route can be carried across mechanisms. It is not an audit report, a penetration test, or independent approval.

## MLE-CH-15-S06 — Five-Port Transfer

The decision schema is equal across `PORT-MANAGED`, `PORT-CLASSICAL`, `PORT-DEEP`, `PORT-EDGE`, and `PORT-SHARED`. Each port must bind identity, origin, expected builder or process, permitted access, consumer, limitation, and previous-good state.

For `PORT-MANAGED`, exportable provider identities and limits must be captured; opaque state is a failure pressure, not an exemption. For `PORT-CLASSICAL`, feature transformation and estimator bytes join the package. For `PORT-DEEP`, checkpoint, tokenizer or preprocessor, and accelerator-context identities join it. For `PORT-EDGE`, sensor input, constrained runtime, device package, delayed feedback, and rollback state are visible. For `PORT-SHARED`, tenant and workload compatibility remain distinct from fleet policy. The mechanism varies; the **decision**, **evidence**, **authority route**, and limitation remain equal. No port receives automatic authority, deeper status, or a weaker proof because it is fashionable, simple, or shared.

The row contracts stay mechanically distinct. Managed evidence must be exportable; an opaque-provider mutation routes to provider/platform owners and cannot qualify the workload. Classical evidence binds feature order and preprocessing; its injected mismatch routes to data/evaluation owners and simplicity is no waiver. Deep evidence binds run, checkpoint, and preprocessor; a wrong-identity mutation routes to research/platform owners and scale is no proof. Edge evidence binds device package, sensor context, and rollback; a stale-device mutation routes to hardware/operations owners and Benchline implies no safety. Shared evidence binds tenant, compatibility, and recovery; a tenant-collision mutation routes to platform/SRE/security and workload proof cannot become fleet assurance. Each row returns only the bounded integrity result.

An equal port transfer does not require identical formats. A managed service may expose export receipts while an edge package exposes a device manifest. The transfer test asks whether both can identify the subject, reproduce the expectation comparison, locate the consumer boundary, demonstrate the recovery target, and tell a reviewer what remains outside the packet. If one mechanism cannot export an identity needed for a decision, the limitation is evidence, not a reason to omit the decision. That makes port choice a replaceable engineering choice rather than a hidden authority hierarchy.

## MLE-CH-15-S07 — Assessment and Qualification Gate

`MLE-CH-15-ASMT-01` asks the reader to inspect a release packet containing one missing digest, one unsigned provenance record, one same-name dependency from a second index, one absent authorization record, and one mutable previous-good tag. For each, write the observed field, disposition, owning route, and re-entry condition. A pass answer identifies why a passing metric cannot compensate for a missing chain.

**Answer intent:** identify each exact broken identity or expectation, distinguish missing from mismatched evidence, refuse promotion, name the retained owner, and state the evidence needed to re-enter the gate.

The assessment is deliberately a record-reading exercise rather than a verifier tutorial. A learner who can recite a signing command but cannot distinguish a missing expected value from an observed mismatch has not yet made the decision auditable. Conversely, a learner who can point to the exact failed tuple, retain the failure record, and route it to the package, build, platform, or security owner has created evidence another reviewer can use. The desired habit is precise refusal, not maximal tooling.

### Qualification Gate

Issue BL-14 only when the exact identities and bounded evidence are complete, the limitation is explicit, the prior-good target is immutable, and every retained decision has its real owner. Otherwise issue HOLD, REJECT, or REOPEN with the discriminating evidence. The gate does not self-authorize a release, an exception, a security policy, an operational action, or later retirement.

Before recording PASS, make the reviewer state the counterfactual: which single record would make this packet non-releasable? If the answer is “nothing because the model passed evaluation,” the packet has collapsed unrelated decisions. If the answer names a missing digest, a builder mismatch, an unauthorized promotion, an unintended dependency origin, or an unresolved recovery target, the gate remains inspectable. This final question is a compact defense against accidental promotion by confidence language.

## MLE-CH-15-S08 — Durable Handoff

BL-14 is the integrity and recovery packet: candidate subject, dependency inventory and origins, provenance expectations and observations, authorization evidence, declared consumers, previous-good identity, limitations, source notes, currentness triggers, owner routes, and immutable failure history. Its canonical outgoing state is RELEASABLE, not “released.” The next chapter measures serving behavior only for this exact candidate and recovery identity. If runtime, dependencies, interface, serving envelope, permitted use, or authority changes, reopen the appropriate earlier gate rather than editing BL-14 in place.

This chapter ends at the handoff boundary. It creates no provider mutation, image, public artifact, deployment, policy, or release decision. Its usable output is a durable packet that can travel to the serving-envelope decision without pretending that evidence has authority.
